# `consensus` commands

> **Experimental.** The `consensus` command group is hidden and refuses to run
> unless you opt in with the hidden `--experimental` flag or
> `SOLO_PROVISIONER_ENABLE_CONSENSUS=1`. It is not production-ready.

Commands for provisioning and operating Hedera/Hiero consensus nodes via the
solo-operator. This page currently documents the `consensus keys` family;
the full onboarding walkthrough lands with the key-management docs story.

## `consensus keys`

Generate, import, verify, and export the cryptographic material a consensus node
needs, and turn it into the Kubernetes secrets the solo-operator consumes.

A consensus node uses three kinds of keys. The provisioner generates the first two;
the admin key is created in an external wallet and only its public key is provided:

| Key | Purpose | Custody |
|---|---|---|
| **gossip signing** | the node's network identity (roster `gossip_ca_certificate`) | private key in a node-pod secret |
| **gRPC TLS** | the node's TLS cert behind HAProxy | private key in a node-pod secret |
| **admin** | signs `nodeCreate`/`nodeUpdate`/`nodeDelete` (DAB) transactions | created in an external wallet, **never generated by solo-provisioner**; private key stays in the wallet and only the public key goes to Kubernetes |

Key types are selected with `--gossip` / `--tls` / `--admin` (`--admin` is the admin
public key, which `generate` never creates). When none is given, all apply.

### `consensus keys generate`

Generate key material into a local folder as enhanced PEM (separate private key
and public certificate/key). Generation is **node-id-free by default**: the
gossip certificate CN is the machine UUID and the gRPC certificate CN is
`localhost`, so the material is valid *before* the network assigns a node-id
during a DAB join.

For a DAB join you need three public values: the gossip certificate
(`s-public.pem`), the SHA-384 hash of the gRPC certificate, and the admin public
key from your wallet. The hash is taken over the certificate in PEM form, as
`nodeCreate` requires. The command prints it to stdout (it is the one value not
otherwise on disk; recompute it any time with `openssl dgst -sha384` over
`hedera.crt`). solo-provisioner does **not** generate the admin key and does
**not** submit the transaction — your wallet or SDK does both.

```bash
# All key types, node-id-free (typical for a DAB join):
sudo solo-provisioner consensus keys generate --experimental \
  --keys-dir ./node-keys --identity my-operator

# Only the gossip signing key:
sudo solo-provisioner consensus keys generate --experimental \
  --keys-dir ./node-keys --gossip
```

`--keys-dir` is one node's folder. For a genesis network with multiple nodes,
run `generate` once per node into its own `--keys-dir`. When several nodes share
one machine (testing), also give each a distinct `--machine-id` so their gossip
certificate CNs differ:

```bash
for i in 0 1 2; do
  sudo solo-provisioner consensus keys generate --experimental \
    --keys-dir ./keys/node$i --machine-id test-node$i
done
```

On real hardware each node is its own host with a unique `/etc/machine-id`, so no
override is needed.

To also create the Kubernetes secrets in one step (known node-id), use
`consensus keys init` (see the key-management docs story).

#### Flags

| Flag | Description | Default |
|---|---|---|
| `--keys-dir` | Directory for this node's key material (required); make it node-specific | — |
| `--identity` | Optional human-readable label recorded in the gossip certificate OU/SAN (e.g. operator or host name) | — |
| `--machine-id` | Override the gossip certificate CN; defaults to the host machine UUID (`/etc/machine-id`) | host machine UUID |
| `--gossip` | Generate the gossip signing key | all types when no selector is given |
| `--tls` | Generate the gRPC TLS key | all types when no selector is given |
| `--grpc-cn` | Common name (subject and issuer) of the gRPC TLS certificate | `localhost` |
| `--grpc-org` | Organization (subject and issuer O) of the gRPC TLS certificate | omitted |
| `--grpc-dns` | Extra fully qualified DNS SAN for the gRPC TLS certificate, added to `localhost` (repeatable) | — |
| `--grpc-ip` | Extra IP SAN for the gRPC TLS certificate, added to `127.0.0.1` and `::1` (repeatable) | — |
| `--grpc-validity-days` | gRPC TLS certificate lifetime in days (1-36500) | 100 years |
| `--overwrite` | Replace existing key files in `--keys-dir` with new keys. This gives the node a new network identity and a new gRPC certificate hash | `false` |

The gRPC TLS certificate always keeps the `localhost`, `127.0.0.1`, and `::1`
SANs; `--grpc-dns` and `--grpc-ip` only add to them. `--grpc-dns` takes a fully
qualified name (at least one dot, e.g. `node2.example.org`); a bare name like
`node2` is rejected. `--grpc-cn` and `--grpc-org` set the subject CN and O, and so the issuer, of
this self-signed certificate (free text, up to 64 characters each). Shell-quote values with
spaces, e.g. `--grpc-org "Example Org"`. The
gossip certificate lifetime is fixed at 100 years because it is the node's network
identity. If the gRPC key already exists in `--keys-dir`, the `--grpc-*` flags have
no effect unless you pass `--overwrite`.

`generate` is node-id-free — it takes no `--node-id`. The node-id enters later,
at `import`/`init`.

Generation is **idempotent**: re-running with the same `--keys-dir` keeps any key
type that already exists (it logs a warning and only fills in missing types), so
it never silently overwrites a node's gossip identity. Pass `--overwrite` to
regenerate. The root `--force`/`-y` flag (skip prompts) does not replace keys.

> **Caution:** Do not use `--overwrite` on a node that is already in a network.
> It replaces the node's gossip identity and its gRPC certificate hash, so the
> node no longer matches the roster until you register the new keys.

#### Output layout

Files use neutral, index-free names that match the Kubernetes secret inner-keys,
so `keys import` maps a generated folder to secrets one-to-one:

| File | Contents |
|---|---|
| `s-private.pem` | gossip signing private key (PKCS#8) |
| `s-public.pem` | gossip signing certificate |
| `hedera.key` | gRPC TLS private key |
| `hedera.crt` | gRPC TLS certificate |

Private key files are written with `0600` permissions. No combined artifacts
file is written — the join inputs are these files plus the gRPC certificate hash
printed at generation time.

### `consensus keys import`

Read the selected key material from a folder and create the per-node
Kubernetes secrets the solo-operator consumes. `--node-id` is required — it
selects which per-node secrets to write.

Each secret is named by the key's own date and fingerprint:

| Secret | Name |
|---|---|
| gossip signing key and certificate | `node<N>-gossip-keys-<date>-<fp8>` |
| gRPC TLS key and certificate | `node<N>-grpc-tls-keys-<date>-<fp8>` |
| admin public key | `node<N>-admin-pubkey-<fp8>` |

`<date>` is the certificate's `Not before` date (UTC, `YYYYMMDD`), so it never
depends on when the import ran: importing the same folder again, for example after
a cluster reset, gives the same names. `<fp8>` is the first 8 hex characters of the
SHA-384 of the PEM-encoded certificate (or of the raw admin public key, which has no date).
Different key material therefore gets a different name, and importing new keys (a
rotation) creates new secrets next to the live ones instead of replacing them. Each
secret also carries labels (`solo.hiero.org/node`, `solo.hiero.org/key-type`,
`solo.hiero.org/cert-fingerprint`) and annotations with the full SHA-384 and the
certificate expiry, so the secrets can be listed and matched to a roster entry. Use
`--label` to add your own labels, for example a reference to an external system.
When a secret's content is already up to date, `import --label` changes only its
labels; the key data is never sent again, so it cannot be overwritten.

The admin key is **not generated** by solo-provisioner. Create it in an external
wallet, then save its **public** key as hex in `admin.pub` inside `--keys-dir`
(32 bytes for Ed25519, or the 33-byte compressed form for secp256k1). Only that
public key is imported; the private key never reaches the provisioner or the
cluster. With no selector flag, the admin secret is created only when `admin.pub`
exists; pass `--admin` to make it required. The admin secret holds the public key
as **raw bytes**, which is what the solo-operator reads; `admin.pub` itself is hex
text, so `import` decodes it and `export` writes it back as hex. The gossip signing secret
Re-importing identical material is idempotent. A secret of the same name whose
content was edited by hand is refused unless `--overwrite` is passed.

```bash
# Create the secrets for node 0 from a generated folder (add admin.pub first
# to include the admin public key):
sudo solo-provisioner consensus keys import --experimental \
  --namespace my-orbit --node-id 0 --keys-dir ./node-keys

# Only refresh the gRPC TLS secret:
sudo solo-provisioner consensus keys import --experimental \
  --namespace my-orbit --node-id 0 --keys-dir ./node-keys --tls
```

| Flag | Description | Default |
|---|---|---|
| `--keys-dir` | Node key folder to import from (required for `--source folder`) | — |
| `--source` | Key material source: `folder` (vault-backed import is tracked separately) | `folder` |
| `--secret-suffix` | Replace the certificate date in the secret names (for example `v0.75.6`); lowercase letters, digits, `-` and `.` | certificate date |
| `--label` | Extra label for every secret, as `key=value` (repeatable), for example `example.com/external-ref=ticket-42` or `app.kubernetes.io/version=v0.75.6`. Kubernetes label syntax applies, and weaver's own labels cannot be used | — |
| `--overwrite` | Replace a same-named secret whose content differs (for example one edited by hand); re-importing identical material is idempotent without it | `false` |
| `--gossip` / `--tls` / `--admin` | Select which secrets to create | gossip and gRPC, plus admin when `admin.pub` exists |

`--namespace` (the orbit name) and `--node-id` are inherited from `consensus
node`; `--node-id` is **required** here.

### `consensus keys export`

Read the selected per-node secrets from the cluster and write their contents to a
folder — a backup, or to move a node's material between namespaces. The admin
secret holds only the public key, so the admin **private** key cannot be
recovered from the cluster; it stays in your wallet.

```bash
sudo solo-provisioner consensus keys export --experimental \
  --namespace my-orbit --node-id 0 --keys-dir ./node0-backup
```

| Flag | Description | Default |
|---|---|---|
| `--keys-dir` | Node key folder to export into (required) | — |
| `--fingerprint` | Pick the secret whose SHA-384 fingerprint starts with this (4+ hex characters); needs exactly one of `--gossip`/`--tls`/`--admin` | — |
| `--secret-suffix` | Pick the secrets imported with this suffix or date | — |
| `--overwrite` | Replace existing files whose content differs (identical files are left as-is) | `false` |
| `--gossip` / `--tls` / `--admin` | Select which secrets to export | all when none given |

Export reads the secret's data and checks it against the secret's name and
fingerprint label; a secret that was renamed or edited is refused. When a node has
more than one generation of a key type, pass `--fingerprint` or `--secret-suffix` to
choose one; otherwise the command lists the candidates and stops.

Export writes only the expected files for each key type: `s-private.pem` (0600)
and `s-public.pem` for gossip, `hedera.key` (0600) and `hedera.crt` for gRPC TLS,
and `admin.pub` for admin. Any other entry is logged and skipped; it stays only in
the cluster secret, not in the backup. A secret that lacks one of its expected
entries is refused.

Export is idempotent: identical files are left untouched, and a file that holds
different content is refused unless `--overwrite` is passed.

`--namespace` and `--node-id` are inherited from `consensus node`; `--node-id` is
**required** here.

### `consensus keys verify`

Validate that the selected key material is well-formed. Verify a folder with `--keys-dir`, or the in-cluster secrets with `--from-cluster --node-id N`. Checks:

- private keys and certificates parse as enhanced PEM;
- each certificate's public key matches its private key;
- the gossip signing key is RSA-3072;
- the admin public key is a valid Ed25519 (32-byte) or secp256k1 (33-byte
  compressed) key. In a folder with no selector flag, `admin.pub` is checked only
  when it exists; the admin private key stays in your wallet and is never read.

The command prints a per-key report and exits non-zero if any check fails.

```bash
# Validate a folder before importing:
sudo solo-provisioner consensus keys verify --experimental --keys-dir ./node-keys

# Validate what is actually in the cluster:
sudo solo-provisioner consensus keys verify --experimental \
  --from-cluster --namespace my-orbit --node-id 0
```

| Flag | Description | Default |
|---|---|---|
| `--keys-dir` | Node key folder to validate | — |
| `--from-cluster` | Validate the in-cluster per-node secrets instead of a folder (requires `--node-id`) | `false` |
| `--fingerprint` | With `--from-cluster`, pick the secret whose SHA-384 fingerprint starts with this (4+ hex characters); needs exactly one of `--gossip`/`--tls`/`--admin` | — |
| `--secret-suffix` | With `--from-cluster`, pick the secrets imported with this suffix or date | — |
| `--gossip` / `--tls` / `--admin` | Select which key types to check | all when none given |

`--keys-dir` and `--from-cluster` are mutually exclusive; `--from-cluster` requires
the inherited `--namespace` and `--node-id`. In the cluster, each secret is checked
against its name and fingerprint label (a renamed or edited secret fails), and when a
node has several generations of a key type the failing line lists them so you can
choose with `--fingerprint` or `--secret-suffix`.

### `consensus keys inspect`

Show the details of the certificates and public keys in a key folder, without needing `openssl`. It covers what `openssl x509 -text -noout`
shows: subject, issuer, validity (with days remaining), signature algorithm, key
type and size, SANs, key usage, SHA-256 and SHA-384 fingerprints (the SHA-256 is over the certificate DER, like
`openssl x509 -fingerprint`; the SHA-384 is over the PEM form, so for the gRPC
certificate it is the roster `grpc_certificate_hash`), and the admin public
key in hex.

Private key files are never read, so nothing secret is loaded into memory. To check
that keys match their certificates, use `consensus keys verify`. Use `--output json` for
machine-readable output. `inspect` shows the commonly needed fields. For every field (modulus, extensions,
raw signature), use `openssl x509 -in <file> -text -noout`. To check that each
private key matches its certificate or public key, use `consensus keys verify`;
`inspect` never reads private keys. Text output ends with a one-line reminder of
both.

Files that are not in the folder are skipped and listed at the end. The command
exits non-zero only if no key file is found or a file does not parse.

```bash
# Inspect a folder:
sudo solo-provisioner consensus keys inspect --experimental --keys-dir ./keys/node0

# Inspect only the gRPC certificate:
sudo solo-provisioner consensus keys inspect --experimental --keys-dir ./keys/node0 --tls

# Inspect what is in the cluster: export it to a folder first, then inspect.
sudo solo-provisioner consensus keys export --experimental \
  --namespace my-orbit --node-id 0 --keys-dir ./exported
sudo solo-provisioner consensus keys inspect --experimental --keys-dir ./exported

# Inspect a single certificate or admin public key file:
sudo solo-provisioner consensus keys inspect --experimental --file ./keys/node0/hedera.crt
```

| Flag | Description | Default |
|---|---|---|
| `--keys-dir` | Node key folder to inspect | — |
| `--file` | Inspect a single certificate (PEM) or admin public key (hex) file | — |
| `--gossip` / `--tls` / `--admin` | Select which key types to show | all when none given |

`--keys-dir` and `--file` are mutually exclusive. Inspect works on disk only, so
it never reads secrets from the cluster.

### `consensus keys init`

One-shot convenience for a node whose id is already known (genesis / known
assignment): generate the key material into `--keys-dir`, then create the per-node
secrets from it. Equivalent to `keys generate` followed by `keys import --node-id
N`, reusing the same code paths.

For a DAB **join** the node-id is not known until the network assigns it, so use
`keys generate` (node-id-free) then `keys import` separately instead.

```bash
sudo solo-provisioner consensus keys init --experimental \
  --namespace my-orbit --node-id 0 --keys-dir ./keys/node0
```

| Flag | Description | Default |
|---|---|---|
| `--keys-dir` | Directory for this node's generated key material (required); make it node-specific | — |
| `--identity` | Optional human-readable label recorded in the gossip certificate OU/SAN | — |
| `--machine-id` | Override the gossip certificate CN; defaults to the host machine UUID (`/etc/machine-id`) | host machine UUID |
| `--grpc-cn` | Common name (subject and issuer) of the gRPC TLS certificate | `localhost` |
| `--grpc-org` | Organization (subject and issuer O) of the gRPC TLS certificate | omitted |
| `--grpc-dns` | Extra fully qualified DNS SAN for the gRPC TLS certificate, added to `localhost` (repeatable) | — |
| `--grpc-ip` | Extra IP SAN for the gRPC TLS certificate, added to `127.0.0.1` and `::1` (repeatable) | — |
| `--grpc-validity-days` | gRPC TLS certificate lifetime in days (1-36500) | 100 years |
| `--overwrite` | Replace existing key files in `--keys-dir` with new keys, and any same-named secret whose content differs. This gives the node a new network identity and a new gRPC certificate hash | `false` |
| `--gossip` / `--tls` / `--admin` | Select which key types to create | gossip and gRPC, plus admin when `admin.pub` exists |

`--namespace` and `--node-id` are inherited from `consensus keys`; `--node-id` is
**required** here. `init` never generates an admin key: create it in an external
wallet and save its public key (hex) as `admin.pub` in `--keys-dir` before running
`init`. Without that file, no admin secret is created and `init` says so; import it
later with `keys import --admin`.

Re-running `init` keeps the key files that already exist in `--keys-dir`. The
root `--force`/`-y` flag (skip prompts) does not change this.

> **Caution:** Do not use `--overwrite` on a node that is already in a network.
> It generates new keys, so the node gets a new gossip identity and a new gRPC
> certificate hash. The new keys get new secrets (the secret name carries the
> key fingerprint); the old secrets stay in the cluster. When a node has more
> than one generation of a key, `consensus node install` keeps the secrets of the
> running node; for a new install, pick one with `--signing-secret` and
> `--grpc-tls-secret`.

### Try it: end-to-end walkthrough

A quick way to see the whole `consensus keys` family working. Steps 1-3 need no
cluster; steps 4-6 need a reachable cluster with the namespace (Orbit CR) in place.

**1. Generate a node's keys**, with extra gRPC certificate details:

```bash
sudo solo-provisioner consensus keys generate --experimental --keys-dir ./keys/node0 \
  --grpc-cn node0 --grpc-org "Example Org" \
  --grpc-dns node0.example.org --grpc-ip 10.1.2.3 --grpc-validity-days 365
```

Expected: `Generated key material in ./keys/node0`, the `gRPC cert hash (SHA-384)`,
and a "Next steps" list. Re-running the same command prints `nothing to generate`.
`generate` never creates the admin key. Create it in your wallet and save its public
key (hex) as `./keys/node0/admin.pub`; the later steps assume that file exists.

**2. Inspect what was generated:**

```bash
sudo solo-provisioner consensus keys inspect --experimental --keys-dir ./keys/node0
```

Expected: one section per file, headed `[s-public.pem | gossip certificate]`,
`[hedera.crt | gRPC TLS certificate]` and `[admin.pub | admin public key]`. The gRPC
section shows `Subject` and `Issuer` containing `CN=node0` and `O=Example Org`,
`SANs: localhost, node0.example.org, 127.0.0.1, ::1, 10.1.2.3`, and a `Not after` date
about 365 days away. The `SHA-384` value equals the hash printed in step 1. Compare
with `sudo openssl x509 -in ./keys/node0/hedera.crt -text -noout` for the full dump.

Missing files are skipped, not errors. Remove one and run it again:

```bash
sudo rm ./keys/node0/admin.pub
sudo solo-provisioner consensus keys inspect --experimental --keys-dir ./keys/node0
```

Expected: exit code 0 and `Not found (skipped): admin.pub`. Save the wallet's admin
public key as `admin.pub` again before continuing.

**3. Check that the keys are valid and match their certificates:**

```bash
sudo solo-provisioner consensus keys verify --experimental --keys-dir ./keys/node0
```

Expected: `[OK  ]` lines for `gossip`, `grpc` and `admin`, then `All checks passed.`

**4. Create the secrets** (known node id):

```bash
sudo solo-provisioner consensus keys import --experimental \
  --namespace my-orbit --node-id 0 --keys-dir ./keys/node0
```

Expected: the command prints three secrets named like
`node0-gossip-keys-<date>-<fp8>`, `node0-grpc-tls-keys-<date>-<fp8>` and
`node0-admin-pubkey-<fp8>`. `kubectl -n my-orbit get secret --show-labels` lists them
with their `solo.hiero.org/node`, `key-type` and `cert-fingerprint` labels. The
`<date>` is the certificate's `Not before` date and `<fp8>` matches the start of the
SHA-384 that `keys inspect` prints for the same file. Running the import again prints
`(already up to date)`. The admin secret holds only the public key. `keys init` does
steps 1 and 4 in one command, importing `admin.pub` if you saved it first.

**5. Verify and export from the cluster:**

```bash
sudo solo-provisioner consensus keys verify --experimental \
  --from-cluster --namespace my-orbit --node-id 0
sudo solo-provisioner consensus keys export --experimental \
  --namespace my-orbit --node-id 0 --keys-dir ./node0-export
```

Expected: `All checks passed.`, then a folder with the gossip and gRPC files plus
`admin.pub`. To inspect what is in the cluster, run `keys inspect
--keys-dir ./node0-export` on the exported folder; `inspect` never reads cluster
secrets or private key files.

**6. Check that bad input is rejected** (each command exits non-zero):

```bash
sudo solo-provisioner consensus keys generate --experimental --keys-dir ./keys/bad --tls --grpc-dns node2
sudo solo-provisioner consensus keys generate --experimental --keys-dir ./keys/bad --tls --grpc-ip not-an-ip
sudo solo-provisioner consensus keys generate --experimental --keys-dir ./keys/bad --tls --grpc-validity-days 99999
sudo solo-provisioner consensus keys generate --experimental --keys-dir ./keys/bad --tls extra-arg
sudo solo-provisioner consensus keys inspect --experimental --keys-dir ./empty-dir
```

Expected: an error for a name that is not fully qualified, an invalid IP, a validity
out of range, an unexpected argument, and a folder with no key files.
